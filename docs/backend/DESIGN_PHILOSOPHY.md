# 설계 철학 (Design Philosophy)

> 이 문서는 [RULES.md](./RULES.md)의 상위 문서이다. 규칙의 **근거(rationale)** 를 설명하며, 규칙에 없는 새로운 상황에서 판단 기준을 제공한다.

---

## 문서 트리거 조건

| 작업 유형                         | 이 문서를 읽어야 하는가? |
|-------------------------------|----------------|
| 기존 규칙으로 판단이 안 되는 새로운 설계 결정    | **필수**         |
| 새 도메인/모듈 추가 시 구조 결정           | **필수**         |
| 기존 규칙의 의도/배경이 궁금할 때           | 권장             |
| 규칙 간 충돌이 발생했을 때               | **필수**         |
| 코드 리뷰에서 "왜 이렇게 하는가" 설명이 필요할 때 | 권장             |

---

## 이 문서의 배경

이 프로젝트의 아키텍처는 교과서에서 패턴을 골라 적용한 결과가 아니다.
개발 과정에서 실제로 부딪힌 문제 — 도메인 간 의존이 꼬여서 한 곳을 고치면 세 곳이 깨지는 상황, 조회 최적화가 비즈니스 로직을 오염시키는 상황, 새 역할을 추가할 때마다 기존 분기문을 전부 수정해야 하는
상황 — 를 해결하는 과정에서 자연스럽게 자리잡은 구조다.

따라서 CQRS, Hexagonal, DDD, Strategy 같은 이름은 사후에 붙인 라벨이지, 설계의 출발점이 아니다.
출발점은 항상 **"이 문제를 어떻게 하면 반복하지 않을까"** 였고, 그 답이 축적되어 지금의 규칙이 되었다.

## 1. 핵심 원리: 경계를 긋고 방향을 강제한다

이 프로젝트의 모든 설계 결정은 하나의 질문에서 출발한다:

> **"변경이 발생했을 때, 그 영향이 어디까지 퍼지는가?"**

영향 범위를 최소화하려면 두 가지가 필요하다:

1. **경계(Boundary)** — 모듈, 도메인, 계층 사이에 명확한 벽을 세운다
2. **방향(Direction)** — 의존은 항상 한쪽으로만 흐르게 강제한다

경계가 있으면 변경이 벽 너머로 퍼지지 않고, 방향이 있으면 변경의 파급을 추적할 수 있다.
13대 원칙, 아키텍처 패턴, 코딩 컨벤션 — 전부 이 두 가지를 서로 다른 레벨에서 실현하는 수단이다.

### 레벨별 경계와 방향

| 레벨  | 경계                         | 방향                        | 구현 수단                                                                                                                          |
|-----|----------------------------|---------------------------|--------------------------------------------------------------------------------------------------------------------------------|
| 모듈  | `libs/backend` 5개 모듈       | `common → ... → apps` 단방향 | Module Boundary (→ [RULES.md §1.2](./RULES.md#12-모듈-경계-module-boundary--critical))                                             |
| 도메인 | Bounded Context            | Port/이벤트로만 소통             | DDD + Vertical Slicing (→ [ARCHITECTURE.md §3.3](./rules/ARCHITECTURE.md#33-ddd-bounded-context--vertical-slicing--critical))  |
| 계층  | api / service / repository | Adapter → Port ← Domain   | Hexagonal Architecture (→ [ARCHITECTURE.md §3.2](./rules/ARCHITECTURE.md#32-hexagonal-architecture-ports--adapters--critical)) |
| 클래스 | Command / Query 분리         | 상호 호출 금지                  | CQRS (→ [ARCHITECTURE.md §3.1](./rules/ARCHITECTURE.md#31-cqrs-command--query-분리--critical))                                   |
| 메서드 | 하나의 책임                     | 입출력이 명확한 계약               | SRP + Design by Contract (→ [RULES.md §1.1](./RULES.md#11-개발-철학-13대-원칙))                                                       |

## 2. 이 원리가 각 패턴을 선택한 이유

### 왜 CQRS인가

읽기와 쓰기는 변경 이유가 다르다. 조회 최적화(DTO Projection, 캐시)와 비즈니스 규칙 적용(검증, 이벤트 발행)을 같은 클래스에 두면, 한쪽을 고칠 때 다른 쪽이 깨질 수 있다.
물리적으로 분리하면 각각 독립적으로 진화한다.

### 왜 Hexagonal인가

도메인 로직은 오래 살고, 인프라(DB, 외부 API, 프레임워크)는 자주 바뀐다.
도메인이 인프라에 직접 의존하면 인프라 교체 시 도메인 코드가 깨진다.
Port 인터페이스로 격리하면 인프라를 교체해도 도메인은 그대로다.

### 왜 DDD Bounded Context인가

도메인 간 직접 참조를 허용하면, 하나의 엔티티 변경이 여러 도메인의 서비스/리포지토리/DTO를 연쇄적으로 깨뜨린다.
Port/이벤트/ID로만 소통하면, 변경 영향이 Port 구현체(Adapter)에서 멈춘다.

### 왜 Strategy Pattern인가

`if-else`/`switch` 분기는 새 타입 추가 시 기존 코드를 수정해야 한다 (OCP 위반).
Strategy + Factory로 분리하면 새 타입은 새 클래스만 추가하면 되고, 기존 코드는 손대지 않는다.

### 왜 Event-Driven Logging인가

로깅은 부수효과(side effect)다. 핵심 비즈니스 로직 안에 로깅 코드가 섞이면 SRP를 위반하고, 트랜잭션 경계도 복잡해진다.
이벤트로 분리하면 핵심 로직은 깨끗하게 유지되고, 로깅은 독립적으로 실패/재시도할 수 있다.

### 왜 Immutability First인가

가변 상태는 "지금 이 값이 무엇인지" 추적해야 하므로 버그의 근원이 된다.
`record`, `final`, 방어적 복사를 기본값으로 쓰면 한번 만든 객체의 상태를 신뢰할 수 있다.
특히 DTO와 이벤트는 생성 후 변경될 이유가 없으므로 불변이 자연스럽다.

## 3. 트레이드오프: 무엇을 포기하는가

모든 설계 결정에는 대가가 있다. 이 프로젝트가 **의도적으로 감수하는 비용**을 명시한다.

| 얻는 것           | 포기하는 것                     | 감수하는 이유                                        |
|----------------|----------------------------|------------------------------------------------|
| 도메인 간 독립성      | Port/Adapter 보일러플레이트       | 도메인이 3개 이상이면 독립성의 이익이 보일러플레이트 비용을 넘는다          |
| 읽기/쓰기 독립 진화    | 클래스 수 증가 (Command + Query) | 클래스가 작으면 탐색이 빠르고, AI 도구가 처리하기 쉽다               |
| 타입 확장 용이 (OCP) | Strategy 초기 구조 비용          | 구체 클래스가 하나뿐이어도 구조를 미리 잡으면 추가 비용이 0에 수렴한다       |
| 인프라 교체 용이      | Port 인터페이스 유지 비용           | 현재 교체 계획이 없어도, 테스트에서 Mock 교체가 용이하다는 즉각적 이점이 있다 |
| 예측 가능한 구조      | 빠른 프로토타이핑                  | 이 프로젝트는 프로토타입이 아니라 장기 운영을 목표로 한다               |

### 이 프로젝트가 하지 않는 것

- **과도한 추상화**: 도메인 내부에서 같은 도메인의 Repository를 직접 쓰는 것은 허용한다. Port로 감싸지 않는다.
- **CQRS의 물리적 DB 분리**: 논리적 분리(클래스 분리)만 한다. 별도 읽기 DB는 운영하지 않는다.
- **이벤트 소싱**: 이벤트는 로깅/알림용이다. 상태 복원 수단이 아니다.
- **마이크로서비스**: 모노레포 + 모듈 경계로 충분하다. 네트워크 경계는 현재 필요하지 않다.

## 4. 판단 프레임워크: 규칙에 없는 상황

새로운 설계 결정이 필요할 때, 아래 질문을 순서대로 던진다.

### 4.1 경계 판단

```text
Q1. 이 코드는 어떤 경계를 넘는가?
    ├─ 도메인 경계를 넘는다 → Port/이벤트를 사용한다
    ├─ 모듈 경계를 넘는다 → 의존 방향(하위→상위)을 확인한다
    ├─ 계층 경계를 넘는다 → 의존이 안쪽(도메인)을 향하는지 확인한다
    └─ 경계를 넘지 않는다 → 직접 호출해도 된다
```

### 4.2 책임 판단

```text
Q2. 이 로직은 읽기인가, 쓰기인가?
    ├─ 읽기 → QueryService에 둔다
    ├─ 쓰기 → CommandService에 둔다
    └─ 둘 다 → 분리할 수 있는지 먼저 검토한다. 불가능하면 Command에 두되, 사유를 주석으로 남긴다
```

### 4.3 분기 판단

```text
Q3. 타입/역할에 따라 동작이 달라지는가?
    ├─ 예 → Strategy Pattern을 적용한다
    └─ 아니오 → 단일 구현으로 충분하다
```

### 4.4 부수효과 판단

```text
Q4. 이 동작은 핵심 로직인가, 부수효과인가?
    ├─ 핵심 로직 → 서비스 메서드 안에 둔다
    └─ 부수효과 (로깅, 알림, 캐시 갱신) → 이벤트로 분리한다
```

### 4.5 최종 검증

결정을 내린 후, 아래 세 가지를 확인한다:

1. **변경 영향**: 이 결정으로 인해 다른 도메인/모듈의 코드를 수정해야 하는가? → 수정해야 한다면 경계가 잘못 그어진 것이다
2. **테스트 용이성**: 이 코드를 단위 테스트할 때 Mock이 3개를 넘는가? → 넘는다면 책임이 과다한 것이다
3. **AI 탐색 용이성**: 클래스명만 보고 역할/계층/도메인을 파악할 수 있는가? → 파악할 수 없다면 네이밍이 부족한 것이다

## 5. 규칙 간 충돌 시 우선순위

규칙이 서로 충돌할 때, 아래 순서로 우선한다:

| 우선순위 | 원칙                         | 근거                          |
|------|----------------------------|-----------------------------|
| 1    | **경계 보전** (도메인 간 직접 참조 금지) | 경계가 무너지면 다른 모든 규칙이 무의미해진다   |
| 2    | **의존 방향** (항상 안쪽으로)        | 방향이 뒤집히면 변경 파급을 추적할 수 없다    |
| 3    | **SRP** (단일 책임)            | 책임이 섞이면 변경 이유가 불명확해진다       |
| 4    | **Fail Fast** (문제 즉시 드러내기) | 암묵적 실패는 디버깅 비용을 기하급수적으로 늘린다 |
| 5    | **Clean Code** (가독성)       | 읽기 쉬운 코드가 유지보수 비용을 줄인다      |

예시: "Port 인터페이스를 만들면 파일이 늘어나서 Clean Code에 어긋나는 것 아닌가?"
→ 경계 보전(1순위)이 가독성(5순위)보다 우선하므로, Port를 만든다. 단, 네이밍을 명확히 하여 가독성 손실을 최소화한다.
